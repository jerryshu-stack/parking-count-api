Parking Count API

Upload a photo of a parking lot with its coordinates. A vision model running on the host machine counts the empty spaces and stores the result. Five endpoints, JSON over HTTPS.

Base URL https://dawn-trace-ratio-went.trycloudflare.com
Before you integrate

The base URL is temporary. It comes from a Cloudflare quick tunnel and changes every time the tunnel restarts. Don't hard-code it — read it from config, and expect to be handed a new one.

The API key is sent separately. It is not printed in this document. Everywhere below, <API_KEY> means the key you were given.

Authentication

All five endpoints require a shared key in the X-API-Key request header. There are no user accounts and no tokens — every caller uses the same key.

X-API-Key: <API_KEY>

A missing or incorrect key returns 401 with body {"detail":"invalid or missing X-API-Key"}. Because the key travels as a plain header, always call over https:// — never http://.

Endpoints

POST /upload multipart/form-data

Submits one image and its coordinates. The request blocks while the model runs, then returns the stored record.

Request fields
FieldTypeDescription
image file required The photo. Any format the model can decode — JPEG and PNG are verified.
latitude float required Where the photo was taken. Stored verbatim; never validated or range-checked.
longitude float required As above.
name string optional Car park name, if you know it. Free text, stored verbatim.
price string optional Fee description, if you know it. Free text — no format is imposed.
total integer optional Total car spaces at the site. Omit it and the record stores null, never 0. A non-integer returns 422.

Omit either and it is stored as an empty string, never dropped. A phone taking a photo normally knows neither, so uploaded records usually carry "" for both.

Example request
curl -X POST https://dawn-trace-ratio-went.trycloudflare.com/upload \
  -H "X-API-Key: <API_KEY>" \
  -F "image=@lot.jpg" \
  -F "latitude=25.0330" \
  -F "longitude=121.5654" \
  -F "name=Taipei 101 B3" \
  -F "price=100 NTD/hr" \
  -F "total=228"
200 response
{
  "count": 12,
  "latitude": 25.033,
  "longitude": 121.5654,
  "timestamp": "2026-09-12T06:47:48Z",
  "name": "Taipei 101 B3",
  "price": "100 NTD/hr",
  "total": 228,
  "source": "photo",
  "image": "2acc83d61c7047619a49688e7b0d07f6.jpg"
}

The response is the single new record — not the full list. count is the model's estimate of empty spaces, a non-negative integer. timestamp is UTC, second precision, recorded when the request arrived rather than when the model finished. image is the stored copy of your upload — an opaque generated name, not the filename you sent. Retrieve it with GET /image; there is no URL that serves it by name.

Records created this way always carry image and source: "photo". Imported records are the mirror image — see Where a record came from below.

Timing

Inference is synchronous and typically takes 2–8 seconds, dominated by model time rather than upload. Set your client timeout to at least 60 seconds. There is no job queue: concurrent requests are processed one after another by the model, so latency climbs under parallel load.

Ordering and size

Oldest first. Records come back in the order they were written, so the newest entry is the last element — reverse the array if you want newest-first. There is no pagination, no limit parameter, and no filtering: the entire history is returned on every call, and the payload grows without bound as uploads accumulate.

GET /nearby query parameters

Returns the records that fall within a radius of a point.

Query parameters
ParameterTypeDescription
latitude float required Centre of the search.
longitude float required Centre of the search.
radius float required Metres. Must be >= 0; a negative value returns 422. The boundary is inclusive, so a record exactly radius away is included.
Example request
curl -G https://dawn-trace-ratio-went.trycloudflare.com/nearby \
  -H "X-API-Key: <API_KEY>" \
  -d latitude=25.0330 -d longitude=121.5654 -d radius=1000
200 response
[
  {
    "count": 19,
    "latitude": 25.033,
    "longitude": 121.5654,
    "timestamp": "2026-09-12T06:57:55Z",
    "distance_m": 0.0
  },
  {
    "count": 12,
    "latitude": 25.0075,
    "longitude": 121.462,
    "timestamp": "2026-09-12T06:38:40Z",
    "distance_m": 10797.6
  }
]

Same record shape as /results plus distance_m — metres from the search centre, rounded to one decimal. Sorted nearest first, unlike /results. An empty array means nothing matched, not an error.

How distance is measured

Great-circle (haversine) distance on a sphere of radius 6 371 008.8 m. Verified against published figures: London → Paris 343.6 km, New York → Los Angeles 3 935.8 km. Because the Earth is not a sphere, expect up to about 0.3% deviation from ellipsoidal (WGS 84) distances — a few metres per kilometre.

GET /image binary image

Returns the stored photo for a coordinate as raw image bytes — not JSON, not a URL. The Content-Type follows the stored file, typically image/jpeg or image/png.

Query parameters
ParameterTypeDescription
latitude float required Matched with the same 1e-6 degree tolerance as DELETE.
longitude float required As above.
Example request
curl -G https://dawn-trace-ratio-went.trycloudflare.com/image \
  -H "X-API-Key: <API_KEY>" \
  -d latitude=25.0330 -d longitude=121.5654 \
  -o lot.jpg
When several records share a coordinate

The most recent one wins. Uploading twice at the same point leaves both records in /results, but /image only ever returns the newer photo. The older image stays on disk and becomes unreachable through the API.

404 responses

Two different conditions, distinguished by the detail string: "no record at this coordinate" when nothing is stored there, and "record has no stored image" when a record exists but its photo is missing. Records created before image storage existed fall into the second case.

DELETE /results query parameters

Removes every record stored at a coordinate.

Query parameters
ParameterTypeDescription
latitude float required The coordinate to clear.
longitude float required As above.
Example request
curl -X DELETE -G https://dawn-trace-ratio-went.trycloudflare.com/results \
  -H "X-API-Key: <API_KEY>" \
  -d latitude=25.0330 -d longitude=121.5654
200 response
{ "deleted": 7, "remaining": 3 }

Deleting a coordinate that holds nothing is not an error — you get 200 with "deleted": 0. There is no way to delete one record while keeping others at the same coordinate. The stored photos are deleted too, and this cannot be undone.

Coordinate matching

A record matches when both latitude and longitude are within 1e-6 degrees — roughly 11 cm — of the values you send. This is a tolerance, not exact equality, so float noise from a JSON round-trip still matches. It is far too tight to act as a radius search: an offset of 1e-4 degrees (about 11 m) already matches nothing. Use /nearby to find records, then delete by their exact coordinates.

Where a record came from

Not every record comes from a photo. Taipei City's open parking feed is imported periodically, so a single /results or /nearby response mixes two kinds of record that you must handle differently. Every record names its origin in source:

sourceMeaning
"photo" A photo was uploaded and the vision model counted the empty spaces.
"taipei-open-data" Imported from Taipei City's published parking feed; the count is their sensor reading.

The field is always present and never empty, so switch on it rather than inferring origin from which other fields happen to be filled in.

FieldUploaded photoImported feed
count The model's estimate The city's sensor reading
image Always present Absent — /image answers 404
name Whatever you sent, else "" Car park name, in Chinese
price Whatever you sent, else "" Fee description, in Chinese
total Whatever you sent, else null Total car spaces at the site

name and price are always present but may be empty strings, and total is always present but may be null — check for content rather than for the key. image is the one field that can be genuinely absent.

count and total are never cross-checked on upload: if you send a total smaller than the model's count, both are stored as given. Imported rows are checked, and any where the vacancy exceeds capacity is dropped rather than imported.

price is free text, not a number. Imported values are the city's own fee paragraph and can run to 300 characters, covering hourly rates, monthly passes, motorcycles and night tariffs at once. Do not try to parse it into a rate; render it, or ignore it.

What the import covers

About 1 050 car parks, all inside Taipei City. The feed lists roughly 1 770. Rows are skipped when they have no live vacancy reading, and also when the reading fails a sanity check against the site's declared car capacity — the source publishes a few impossible rows (one reports 900 free spaces out of 6) and some bus- or motorcycle-only sites where the car vacancy field does not describe cars. Coordinates are converted from TWD97 to WGS84 during import; the source publishes the car park centroid, so expect the point to sit tens of metres from the actual entrance.

Every imported record shares one timestamp — the feed's own publish time, not the moment each lot was measured. A re-import replaces the whole imported set, so those timestamps all move together and the counts jump to the new reading. Imported records are a snapshot, not a history.

Known limits

This is a proof of concept, not a production service. These are not bugs to report — they are things to design your client around.

  • No upload size limit. The whole file is read into memory. Resize photos client-side before sending.
  • No rate limiting. Nothing stops a caller from saturating the model. Be a good neighbour — serialize your requests.
  • Writes can be lost. Storage is a single JSON file rewritten on every upload; two simultaneous uploads can overwrite each other. Avoid concurrent POSTs.
  • Counts are model estimates. Accuracy has not been measured against labelled ground truth. Treat count as an approximation, not a reading from a sensor.
  • Deletes are by coordinate, not by record. DELETE /results clears every record at a point at once. There is no record ID and no way to update one in place — to replace a reading, delete the coordinate and upload again.
  • Imported records can be replaced without warning. A re-import deletes every record with source: "taipei-open-data" and writes fresh ones. Coordinates stay stable, so a DELETE you issued against an imported point comes back on the next import.
  • Photos are stored forever, and unevenly. Every upload writes a file that is only removed when its coordinate is deleted. Because /image serves just the newest record at a point, repeated uploads at one coordinate accumulate files no request can reach.
  • Search scans everything. /nearby reads the whole file and measures every record on each call. There is no spatial index; it degrades linearly as data grows.
  • The host may be offline. The service runs on a single desktop machine behind a tunnel; expect connection failures and retry.

Browser client

Opening the base URL in a browser serves a small mobile page for picking a photo and submitting it. That page is the only unauthenticated route — GET / returns HTML without a key, so that a phone can load it. It asks for the key once and keeps it in localStorage.
